# Review and grade, October 2026

A review of the whole platform with the evidence for each grade, what was changed because of it, and what still holds each grade back. The grades are for a research platform and teaching tool that one person runs on their own computer or on Replit, not for a service with many users. **A** means nothing I could find is left to fix at that scale; **B** that it works and has a known gap; **C** that it works for whoever built it and breaks for someone else.

How the evidence was gathered: the repository at the start of the round (commit `959af75`) and its CI; a fresh run of every check named below; an accessibility audit of every dashboard view in a real browser (axe-core, 11 tabs, light and dark); a read of the user's Replit app through the Replit connector (its files and job records, read only, nothing changed); and live calls to the public services the app uses. iTick was never called with a working key by the reviewer.

## Correctness and tests: A-

3,123 tests in 160 files. Every library strategy and every machine-learning feature is tested for causality by replacing the future with noise and checking that nothing changes; the backtest engine's profit and loss is recomputed independently through futures rolls, cash and margin; searches and verdicts are tested against synthetic strategies whose truth is known; the dashboard is driven in a real Chromium. One browser test (the arrow keys on the tabs) failed about one run in seven once the Forecast tab had been added; the cause was a race in the Guides tab (a slow guide index brought the tab back after the reader had left it), which is fixed and has a test of its own that fails without the fix. Coverage is 90.7% (4,132 of 44,614 statements unrun) and CI fails below 88%. What holds the grade back: the suite takes about 25 minutes on a CI runner, and the tests are never checked by planting bugs.

## Continuous integration: B to A-

Before the round the workflow had four jobs: the full suite on Python 3.11, the numerical packages on 3.10 and 3.12, ruff and the Docker image. Three gaps. The tests that drive the dashboard in a real Chromium were *skipped* in CI (without Playwright they are skipped silently), so the whole front end was untested there. Replit runs Python 3.10, and the dashboard and the machine-learning tab were only ever run on 3.11. The documentation site was never built, and it had a broken link (`../README.md`). Now: a `browser` job installs Chromium and runs the seven browser test files; a `replit-python` job runs the dashboard, iTick, tuning and machine-learning tests on 3.10; a `docs` job builds the site with `mkdocs --strict`; a newer push cancels the older run of the same branch; the test job fails below 88% coverage, where before it only reported the figure. The first run of the browser job passed. Ruff checked 7 groups of rules and now checks 17 (unused variables, mutable default arguments, `raise` without `from`, comparisons with `None`, bare `except`), and the widened rules found and removed dead code.

## Security: B- to B+

The server already sent a content-security policy and `nosniff`. It read `Content-Length` with `int(... or 0)`: a negative or non-numeric value made a handler wait for bytes that never came, and a client that connected and sent nothing held a thread for ever. Now: a bad `Content-Length` is refused at once, a silent connection is dropped after 30 seconds, every answer carries the full set of headers (CSP with `base-uri`, `object-src`, `form-action` and `frame-ancestors`, referrer policy, cross-origin policies, permissions policy; no Python version in the `Server` header), and an optional access code (`QUANT_LAB_ACCESS_CODE`, a Replit secret) puts a login page in front of everything, with a `HttpOnly`, `SameSite=Strict` cookie (`Secure` behind an HTTPS proxy) and a limit of ten wrong guesses in five minutes. The iTick key is read from the environment only and never reaches a page, a log, an error or a file (the tests search for it); the refusal messages now say when iTick last took the key, whether it is the same key, and the address iTick sees the app at, so a rejected key can be told from an address restriction. What holds it back: the dashboard's per-launch token is a convenience, not an account system, and the app serves HTTP (Replit supplies the HTTPS).

## Accessibility: C to A-

An axe-core audit of the 11 tabs in light and dark found 126 failing elements in 20 of the 22 views: 72 buttons with `aria-selected` where the role does not allow it, 38 text colours below the WCAG contrast of 4.5:1 (the accent colour among them), 11 views with no top-level heading, 3 headings that skipped a level, 2 unnamed selects. Now: the section tabs are a real tab list (roving `tabindex`, arrow keys, Home and End), choosers that are not tabs are toggle buttons, every view has one `h1` and no skipped level, both themes pass the contrast ratio, every form control has a name, and the audit finds nothing in any of the 22 views. `tests/test_webapp_accessibility.py` keeps each of these found (the contrast test reads the stylesheet and runs without a browser).

## Performance: B to B+

The page's scripts and styles are 546 KB; they now travel as 161 KB when the browser accepts gzip, and a second visit costs a 304 answer (each file has an `ETag`; the page itself and every API answer are `no-store`, because the page carries the token). Anything slow runs as a background job. A Tune search or a machine-learning experiment is a job with a Stop button; the new Gaussian-process search adds about a second a proposal at 40 tries (97 seconds for a search of a real strategy against 65 for the default search), beside a backtest of about a second a try. What holds it back: one worker thread runs one job at a time, so a long search delays what is queued behind it.

## Documentation: A- to A

116 technique guides, 118 strategy cards, a glossary of 302 terms (fifteen added for the forecasting chapter, 29 for option models), a dashboard manual, a tuning chapter that now includes how its thresholds were measured, a machine-learning chapter, and a Replit guide; the site builds with `--strict` in CI, every internal link is tested, and the generated pages are checked against the code.

## Reliability of long runs: B+

Unchanged this round. A run lost in a crash shows as stopped within about a minute, can be cleared, and nothing is checkpointed or resumed (the docs say so). The Replit records show the job log working: backtests, a machine-learning run on three Singapore tickers and a Tune search of 97 seconds all finished and are listed.

## Data connections: B-

Yahoo Finance, Cboe, Deribit, Coinbase, Kraken, Bitstamp and OKX work without a key. iTick has never been called with a working key by the reviewer, and the app's own records on Replit show what happened to the user's: on 13 October iTick said "Your IP address is not allowed" (HTTP 403) and then "no daily bars" for `US:ES` and `US:SI` (the key accepted, the product not on the plan), and on 16 October both iTick hosts refused the key outright ("0 auth failed" and "Invalid API key in request"), which is what a key from an ended trial, a regenerated key or a changed account looks like. The new diagnosis says this in the app. What holds it back: only iTick's dashboard can say which.

## Tuning and machine learning: B+ to A-

The question for this area was whether the search and its verdict can be trusted. On real prices the truth is never known, so it was measured on simulated strategies whose edge is known (`experiments/tune_selection_study.py`: 150 searches of 40 tries in each of twelve kinds of world). The verdict as it was, which called a winner "good" when at least half of its tuning gain showed up on the untouched days, said so for a strategy with **no edge** 21% of the time (14% when the starting settings were already the best there was). The deflated Sharpe ratio was part of the trouble: it counted every try as independent, though settings near each other trade alike and 40 tries are worth 5 to 8, and so it hid real edges (95% reached in 22% and 8% of strong-edge searches). A ✓ now also needs a paired t of the gain of at least 1, a Romano-Wolf p of the winner under 30%, and a check, choosing again on the past alone, that did not lose to the starting settings. A ✓ for no edge fell from 21% to 5% of searches (start already best: 14% to 1%); the share of ✓ that came with a real gain rose from 74% to 85% with a moderate edge and from 93% to 99% with a strong one. The price: ✓ is given less often to real edges (strong edge, 61% to 45%), and the page says *mixed: better, but not by enough to rule out luck*.

The search gained a scrambled Sobol start and an optional Gaussian process (Matérn 5/2, expected improvement). On five noisy test functions with a known best the process had the smallest regret on four (Hartmann-6 at 40 tries: 0.63 against 0.83 for TPE and 1.86 for random draws); on simulated strategies, and on four real ones (36 searches), the searches could not be told apart (the same Sharpe ratio on the days they saw, 0.897 to 0.908). So TPE with the even start stays the default, the process is a choice under *Advanced*, and the middle-of-the-best-region rule, which never beat the highest score, stays optional.

The Machine learning tab's *Tune one model* got the even start, the Gaussian process as a choice, and the same gates with a comparison against holding every ticker. A ridge regression tuned in 16 tries on the 15 ETFs went from −1.05 to 0.42 on validation and from −0.39 to 0.56 on the test and forward days, and the page said *mixed* (Romano-Wolf p 45%; holding every ticker scored 0.94). Nothing here gives a model an edge it does not have. On the four real strategies a ✓ was followed by a gain over the starting settings, on the 5.3 to 5.6 years after the search's data ended, in only about half of the searches: a hold-out is one stretch of one history, and the page says so. What holds the grade back: the thresholds were measured on simulated strategies that never change regime, the real-data runs are small, and the default machine-learning setup has no edge on the ETFs.

## Fit to Replit: B

The records show the app running on Replit and doing real work. Three things to know. The Replit copy is the version from before this round: its `server.py` still reads `Content-Length` with `int(... or 0)` and has no access code, and it lacks the iTick history, the accessibility fixes and the new verdict checks, though the Tune tab is there (a search ran on 16 October). To get the round: `git pull` in the Shell (on this branch), then Stop and Run. On Replit the server listens on an address anyone with the preview link can reach, and the page it serves carries the per-launch token, so *the link is the key*: set the `QUANT_LAB_ACCESS_CODE` secret, which puts a login page in front of everything. The app has never been published (`get_publish_status` says not found). And the Replit Agent could not be asked to confirm any of this: `ask_question` answered "paused" on every try, so what is said here about the Replit app comes from its files and records, not from running it.

## Forecasting: B+ (added after the review)

The Forecast tab and `quant forecast` were built after the grades above were given, so this is a first grade and the only one in the table with no "before". What it is: twenty-two ways to forecast a stock's price as a distribution (Monte Carlo simulation, Markov chains, a hidden Markov model, Gaussian processes, a Kalman filter, volatility models including GARCH with variance-gamma or NIG shocks and Heston, analogues, an equal-weight blend) tested walk forward against a random walk, with a verdict in words ([the chapter](forecasting.md)).

The evidence for the grade. Each method was first run on a market whose truth is known (clustered volatility, two regimes, a planted drift, a planted reversal, jumps, independent returns): it finds what was planted and nothing where nothing was planted. The scores are checked against closed forms (the CRPS of a Gaussian, the fair form against the small-sample bias of the plain one, the Holm adjustment against a reference), a spy method proves that no forecast sees a price from after its date, a pool of forecasts scores no worse than the average of its members as the maths says, the verdict is built from the numbers of the report and nothing else, the API is driven over HTTP and the page in a real Chromium, and an axe-core audit of the form and of a result, in both themes, found nothing. Building it found four things worth recording: an unconstrained Gaussian process fitted 80% to 93% of the variance of pure noise (the noise and length scale are now bounded, and a test finds none in noise); the HAR model's standardised residuals were lined up with the wrong day, which made its tail weight 100 and not 6.7; the hidden Markov model's forecasts are not bit-for-bit repeatable between fits (the contract test allows 1e-7); and a race in the dashboard, found because an accessibility test failed one run in seven, by which the Guides index, if it arrived after the reader had moved to another tab, brought the Guides tab back (fixed, with a test that fails without the fix).

What the real prices said, on the platform's ETFs at the Standard setting (the tables are in the chapter and `python -m experiments.forecast_study` reproduces them): the spread of returns can be forecast a little (on SPY by more than luck allows, on QQQ and EEM by amounts luck could explain, on TLT and GLD not at all); the average return and the direction could not be forecast; the Gaussian process on recent moves added nothing to the volatility-scaled history it builds on; the textbook Gaussian-process forecast of the price path was 63% to 90% worse than the random walk; and an equal-weight blend was the only method never behind the yardstick.

What holds the grade back: one ticker and one horizon per run; the real-data results are one history of five ETFs, over a stretch in which the equity ETFs mostly rose, with about 67 independent 21-day forecasts and 28 independent 63-day ones; daily prices only, with no intraday data, earnings or macro series in any method; the methods are fitted by maximum likelihood or least squares and not by full Bayesian inference; and the Replit copy of the app predates the tab (a `git pull` and a restart bring it).

## Option models and numerical methods: B+ (added after the review)

What was added: five pricing models (Merton, Kou, variance gamma, NIG, Heston) priced by Fourier methods and fitted to a chain; finite-difference and integro-differential solvers for European, barrier, digital and American options; Monte Carlo with control variates; hedging under transaction costs (Leland, Whalley-Wilmott, utility-based prices); stochastic differential equation schemes and exact samplers; short-rate models; Kalman trackers; a closed-form mean-variance frontier; an Ornstein-Uhlenbeck pairs strategy; four forecasting methods; and three views of the Options tab and a `quant models` command that put them in front of the reader. The topics follow the notebooks of Cantaro's *Financial Models Numerical Methods*; that repository is AGPL-3.0 and this one MIT, so none of its code was used, and everything was written from the published mathematics and checked against closed forms, independent methods and simulations with a known truth.

Evidence: about 450 new tests, each module checked against a reference that does not share its code (the Black-Scholes closed form, the Fourier price, an exact simulation, an independent Longstaff-Schwartz estimate, the bond equation, a numerical optimiser with loosened bounds); a bug found in an older function by the first of those checks (the closed-form Merton series counted the jump compensation twice and over-priced by about 4% at two jumps a year); the new views audited with axe-core in light and dark (no violations), tested in a real browser and on a phone width.

What holds it back: **no option quotes**. Every fit in the repository is to the platform's simulated surface, so it shows how the machinery behaves and which family resembles that surface, not what a market believes; a downloaded chain is one delayed snapshot. The Heston model has no American price (two state variables). Hedging results assume a constant proportional cost and a known volatility. And the new forecasters were tested on real prices and did **not** beat GARCH, the new pairs strategy is mostly in cash on the 15 ETFs (its net Sharpe ratio was -0.16), and the page says both: the machinery is built and tested, and the evidence that it adds an edge is, honestly, none yet.
