# Review and grade, October 2026

A review of the whole platform with the evidence for each grade, what was changed because of it, and what still holds each grade back. The grades are for a research platform and teaching tool that one person runs on their own computer or on Replit, not for a service with many users. **A** means nothing I could find is left to fix at that scale; **B** that it works and has a known gap; **C** that it works for whoever built it and breaks for someone else.

How the evidence was gathered: the repository at the start of the round (commit `959af75`) and its CI; a fresh run of every check named below; an accessibility audit of every dashboard view in a real browser (axe-core, 11 tabs, light and dark); a read of the user's Replit app through the Replit connector (its files and job records, read only, nothing changed); and live calls to the public services the app uses. iTick was never called with a working key by the reviewer.

## Correctness and tests: A-

4,021 tests in 200 files (3,123 in 160 at the time of the review). Every library strategy and every machine-learning feature is tested for causality by replacing the future with noise and checking that nothing changes; the backtest engine's profit and loss is recomputed independently through futures rolls, cash and margin; searches and verdicts are tested against synthetic strategies whose truth is known; the dashboard is driven in a real Chromium. One browser test (the arrow keys on the tabs) failed about one run in seven once the Forecast tab had been added; the cause was a race in the Guides tab (a slow guide index brought the tab back after the reader had left it), which is fixed and has a test of its own that fails without the fix. Coverage is about 92% (91.8% at the last complete CI run of the suite, 4,501 of 55,171 statements unrun) and CI fails below 88%. What holds the grade back: the test job takes 32 to 40 minutes on a CI runner and the whole run an hour, with the Docker build that follows it, and the tests have been checked by planting bugs only for the company-fundamentals code (its research code, key pool, credit meter, OpenFilings adapter and years module; `experiments/plant_bugs.py`, run by hand and not in CI; the audit is described under Company fundamentals), not for the rest of the platform.

## Continuous integration: B to A-

Before the round the workflow had four jobs: the full suite on Python 3.11, the numerical packages on 3.10 and 3.12, ruff and the Docker image. Three gaps. The tests that drive the dashboard in a real Chromium were *skipped* in CI (without Playwright they are skipped silently), so the whole front end was untested there. Replit runs Python 3.10, and the dashboard and the machine-learning tab were only ever run on 3.11. The documentation site was never built, and it had a broken link (`../README.md`). Now: a `browser` job installs Chromium and runs the seven browser test files; a `replit-python` job runs the dashboard, iTick, tuning and machine-learning tests on 3.10; a `docs` job builds the site with `mkdocs --strict`; a newer push cancels the older run of the same branch; the test job fails below 88% coverage, where before it only reported the figure. The first run of the browser job passed. Ruff checked 7 groups of rules and now checks 17 (unused variables, mutable default arguments, `raise` without `from`, comparisons with `None`, bare `except`), and the widened rules found and removed dead code.

## Security: B- to B+

The server already sent a content-security policy and `nosniff`. It read `Content-Length` with `int(... or 0)`: a negative or non-numeric value made a handler wait for bytes that never came, and a client that connected and sent nothing held a thread for ever. Now: a bad `Content-Length` is refused at once, a silent connection is dropped after 30 seconds, every answer carries the full set of headers (CSP with `base-uri`, `object-src`, `form-action` and `frame-ancestors`, referrer policy, cross-origin policies, permissions policy; no Python version in the `Server` header), and an optional access code (`QUANT_LAB_ACCESS_CODE`, a Replit secret) puts a login page in front of everything, with a `HttpOnly`, `SameSite=Strict` cookie (`Secure` behind an HTTPS proxy) and a limit of ten wrong guesses in five minutes. The iTick key is read from the environment only and never reaches a page, a log, an error or a file (the tests search for it); the refusal messages now say when iTick last took the key, whether it is the same key, and the address iTick sees the app at, so a rejected key can be told from an address restriction. What holds it back: the dashboard's per-launch token is a convenience, not an account system, and the app serves HTTP (Replit supplies the HTTPS).

## Accessibility: C to A-

An axe-core audit of the 11 tabs in light and dark found 126 failing elements in 20 of the 22 views: 72 buttons with `aria-selected` where the role does not allow it, 38 text colours below the WCAG contrast of 4.5:1 (the accent colour among them), 11 views with no top-level heading, 3 headings that skipped a level, 2 unnamed selects. Now: the section tabs are a real tab list (roving `tabindex`, arrow keys, Home and End), choosers that are not tabs are toggle buttons, every view has one `h1` and no skipped level, both themes pass the contrast ratio, every form control has a name, and the audit finds nothing in any of the 22 views. `tests/test_webapp_accessibility.py` keeps each of these found (the contrast test reads the stylesheet and runs without a browser).

## Performance: B to B+

The page's scripts and styles are 546 KB; they now travel as 161 KB when the browser accepts gzip, and a second visit costs a 304 answer (each file has an `ETag`; the page itself and every API answer are `no-store`, because the page carries the token). Anything slow runs as a background job. A Tune search or a machine-learning experiment is a job with a Stop button; the new Gaussian-process search adds about a second a proposal at 40 tries (97 seconds for a search of a real strategy against 65 for the default search), beside a backtest of about a second a try. What holds it back: one worker thread runs one job at a time, so a long search delays what is queued behind it.

## Documentation: A- to A

123 technique guides, 118 strategy cards, a glossary of 327 terms (fifteen added for the forecasting chapter, 29 for option models, 25 for company fundamentals), a dashboard manual, a tuning chapter that now includes how its thresholds were measured, a machine-learning chapter, and a Replit guide; the site builds with `--strict` in CI, every internal link is tested, and the generated pages are checked against the code.

## Reliability of long runs: B+

Unchanged this round. A run lost in a crash shows as stopped within about a minute, can be cleared, and nothing is checkpointed or resumed (the docs say so). The Replit records show the job log working: backtests, a machine-learning run on three Singapore tickers and a Tune search of 97 seconds all finished and are listed.

## Data connections: B-

Yahoo Finance, Cboe, Deribit, Coinbase, Kraken, Bitstamp and OKX work without a key. iTick has never been called with a working key by the reviewer, and the app's own records on Replit show what happened to the user's: on 13 October iTick said "Your IP address is not allowed" (HTTP 403) and then "no daily bars" for `US:ES` and `US:SI` (the key accepted, the product not on the plan), and on 16 October both iTick hosts refused the key outright ("0 auth failed" and "Invalid API key in request"), which is what a key from an ended trial, a regenerated key or a changed account looks like. The new diagnosis says this in the app. What holds it back: only iTick's dashboard can say which.

## Tuning and machine learning: B+ to A-

The question for this area was whether the search and its verdict can be trusted. On real prices the truth is never known, so it was measured on simulated strategies whose edge is known (`experiments/tune_selection_study.py`: 150 searches of 40 tries in each of twelve kinds of world). The verdict as it was, which called a winner "good" when at least half of its tuning gain showed up on the untouched days, said so for a strategy with **no edge** 21% of the time (14% when the starting settings were already the best there was). The deflated Sharpe ratio was part of the trouble: it counted every try as independent, though settings near each other trade alike and 40 tries are worth 5 to 8, and so it hid real edges (95% reached in 22% and 8% of strong-edge searches). A ✓ now also needs a paired t of the gain of at least 1, a Romano-Wolf p of the winner under 30%, and a check, choosing again on the past alone, that did not lose to the starting settings. A ✓ for no edge fell from 21% to 5% of searches (start already best: 14% to 1%); the share of ✓ that came with a real gain rose from 74% to 85% with a moderate edge and from 93% to 99% with a strong one. The price: ✓ is given less often to real edges (strong edge, 61% to 45%), and the page says *mixed: better, but not by enough to rule out luck*.

The search gained a scrambled Sobol start and an optional Gaussian process (Matérn 5/2, expected improvement). On five noisy test functions with a known best the process had the smallest regret on four (Hartmann-6 at 40 tries: 0.63 against 0.83 for TPE and 1.86 for random draws); on simulated strategies, and on four real ones (36 searches), the searches could not be told apart (the same Sharpe ratio on the days they saw, 0.897 to 0.908). So TPE with the even start stays the default, the process is a choice under *Advanced*, and the middle-of-the-best-region rule, which never beat the highest score, stays optional.

The Machine learning tab's *Tune one model* got the even start, the Gaussian process as a choice, and the same gates with a comparison against holding every ticker. A ridge regression tuned in 16 tries on the 15 ETFs went from −1.05 to 0.42 on validation and from −0.39 to 0.56 on the test and forward days, and the page said *mixed* (Romano-Wolf p 45%; holding every ticker scored 0.94). Nothing here gives a model an edge it does not have. On the four real strategies a ✓ was followed by a gain over the starting settings, on the 5.3 to 5.6 years after the search's data ended, in only about half of the searches: a hold-out is one stretch of one history, and the page says so. What holds the grade back: the thresholds were measured on simulated strategies that never change regime, the real-data runs are small, and the default machine-learning setup has no edge on the ETFs.

## Forecasting: B+ (added after the review)

The Forecast tab and `quant forecast` were built after the grades above were given, so this is a first grade and the only one in the table with no "before". What it is: twenty-two ways to forecast a stock's price as a distribution (Monte Carlo simulation, Markov chains, a hidden Markov model, Gaussian processes, a Kalman filter, volatility models including GARCH with variance-gamma or NIG shocks and Heston, analogues, an equal-weight blend) tested walk forward against a random walk, with a verdict in words ([the chapter](forecasting.md)).

The evidence for the grade. Each method was first run on a market whose truth is known (clustered volatility, two regimes, a planted drift, a planted reversal, jumps, independent returns): it finds what was planted and nothing where nothing was planted. The scores are checked against closed forms (the CRPS of a Gaussian, the fair form against the small-sample bias of the plain one, the Holm adjustment against a reference), a spy method proves that no forecast sees a price from after its date, a pool of forecasts scores no worse than the average of its members as the maths says, the verdict is built from the numbers of the report and nothing else, the API is driven over HTTP and the page in a real Chromium, and an axe-core audit of the form and of a result, in both themes, found nothing. Building it found four things worth recording: an unconstrained Gaussian process fitted 80% to 93% of the variance of pure noise (the noise and length scale are now bounded, and a test finds none in noise); the HAR model's standardised residuals were lined up with the wrong day, which made its tail weight 100 and not 6.7; the hidden Markov model's forecasts are not bit-for-bit repeatable between fits (the contract test allows 1e-7); and a race in the dashboard, found because an accessibility test failed one run in seven, by which the Guides index, if it arrived after the reader had moved to another tab, brought the Guides tab back (fixed, with a test that fails without the fix).

What the real prices said, on the platform's ETFs at the Standard setting (the tables are in the chapter and `python -m experiments.forecast_study` reproduces them): the spread of returns can be forecast a little (on SPY by more than luck allows, on QQQ and EEM by amounts luck could explain, on TLT and GLD not at all); the average return and the direction could not be forecast; the Gaussian process on recent moves added nothing to the volatility-scaled history it builds on; the textbook Gaussian-process forecast of the price path was 63% to 90% worse than the random walk; and an equal-weight blend had the best average skill and the smallest worst case (0.1 points behind the yardstick on TLT, against at least 1.2 points for every other method).

What holds the grade back: one ticker and one horizon per run; the real-data results are one history of five ETFs, over a stretch in which the equity ETFs mostly rose, with about 67 independent 21-day forecasts and 28 independent 63-day ones; daily prices only, with no intraday data, earnings or macro series in any method; the methods are fitted by maximum likelihood or least squares and not by full Bayesian inference; and the Replit copy of the app predates the tab (a `git pull` and a restart bring it).

## Option models and numerical methods: B+ (added after the review)

What was added: five pricing models (Merton, Kou, variance gamma, NIG, Heston) priced by Fourier methods and fitted to a chain; finite-difference and integro-differential solvers for European, barrier, digital and American options; Monte Carlo with control variates; hedging under transaction costs (Leland, Whalley-Wilmott, utility-based prices); stochastic differential equation schemes and exact samplers; short-rate models; Kalman trackers; a closed-form mean-variance frontier; an Ornstein-Uhlenbeck pairs strategy; four forecasting methods; and three views of the Options tab and a `quant models` command that put them in front of the reader. The topics follow the notebooks of Cantaro's *Financial Models Numerical Methods*; that repository is AGPL-3.0 and this one MIT, so none of its code was used, and everything was written from the published mathematics and checked against closed forms, independent methods and simulations with a known truth.

Evidence: about 450 new tests, each module checked against a reference that does not share its code (the Black-Scholes closed form, the Fourier price, an exact simulation, an independent Longstaff-Schwartz estimate, the bond equation, a numerical optimiser with loosened bounds); a bug found in an older function by the first of those checks (the closed-form Merton series counted the jump compensation twice and over-priced by about 4% at two jumps a year); the new views audited with axe-core in light and dark (no violations), tested in a real browser and on a phone width.

What holds it back: **no option quotes**. Every fit in the repository is to the platform's simulated surface, so it shows how the machinery behaves and which family resembles that surface, not what a market believes; a downloaded chain is one delayed snapshot. The Heston model has no American price (two state variables). Hedging results assume a constant proportional cost and a known volatility. And the new forecasters were tested on real prices and did **not** beat GARCH, the new pairs strategy is mostly in cash on the 15 ETFs (its net Sharpe ratio was -0.16), and the page says both: the machinery is built and tested, and the evidence that it adds an edge is, honestly, none yet.

## Company fundamentals: B+ (added after the review; B at first, regraded after a second round)

The Fundamentals tab and `quant fundamentals` were built after the grades above were given, so this is a first grade (B), and the second round below moved it to B+. What it is: a local SQLite database of company statements as filed (the hosted OpenFilings API is a source and a credit meter, never the database); a point-in-time engine that treats a figure as known on its filing date plus a lag, and a restatement as a new version public from the day it was first seen; 84 factors; factor studies (rank IC with an overlap-corrected t-statistic, buckets, a costed long-short, decay, breakdowns by year, country, sector and market regime); a staged formula search that counts every formula it tries and keeps the failures in a graveyard; an alpha library with a fixed table of status changes and a monitor; ways to combine alphas (rules, and models fitted walk-forward with a purge and an embargo); and a bridge that runs a signal as a limited, costed portfolio through the platform's own backtest engine against an equal-weight benchmark ([the chapter](fundamentals.md)). Several keys can be given (the page lists five slots), but the first working one does all the work and the others stand by: OpenFilings' usage policy forbids rotating accounts or keys to get past a quota, so the application never switches by itself. A button (*Use this key*, or `quant fundamentals use-key`) lets its user choose which key is in use; the choice is kept, and refused while the key in use has spent its allowance.

The evidence for the grade. 290 new tests in 16 files, each checked against a truth that does not share its code: nothing is visible before its filing date plus the lag; a world with alphas planted in it gives them back and shows nothing for three ordinary factors, and a placebo world (each date's returns dealt out to other companies at random) gives **no Candidate** in two runs of 200 formulas (a seed that once let a lucky formula through every screen is why the q-value gate exists); altering the returns after a date leaves every earlier combination weight and model prediction unchanged; the engine earns what the factor tests say the same holdings earn, to five millionths, and no limit is ever broken; the DuPont contributions add up to the change in ROE; no key reaches the database, a log, an error or a status line (the tests search for it) and the real transport does not follow a redirect with the key in its headers; the routes are driven over HTTP and the page in a real Chromium, and the axe-core audits of the tab's views, in light and dark, find nothing. Using the tab in a browser found defects the unit tests had not, each fixed with a test: the monitor flipped an alpha's signal a second time, so an alpha used upside down and still working was judged *Broken*; the library showed the training IC unflipped beside flipped validation and locked-block figures; the warnings of a blend were repeated and did not say which alpha they were about; a count of years under a chart was a share printed as a count; one busy state for the whole tab left a view on "Working..." after a quick switch of database and view; a default command-line option (`backtest -n`) silently became 300 because two options shared a destination; and the audit found table headers with no text, meters with no name and text colours that failed the contrast ratio in dark mode. The first use with a real key found one more: *Find a company* searched only the companies already stored, so on an empty database a search for "Nvidia" answered "No company matches" with Country and Sector lists holding only "All" and no way to find a company by name. It now says the database is empty, hides lists with nothing to choose, and searches OpenFilings' directory on request (one credit, the same search again free), with *Add* and *Add and fetch* buttons that state their cost. A later use found another: a company's first fetch (11 credits) brought back only a few years of history, and the tab could neither say why nor let the rest be asked for (the bullet *The years a company holds* under *What was done* is the fix). Six statements in the first draft of the documents were wrong or loose (the tolerance of the engine-agreement test, what *Broken* means, the wording of the Beneish cut-off, which solver handles which size, a claim about how alike three value ratios are, a count of failures at the first test) and were corrected against the code and fresh runs.

What the demo world said, to show the machinery works and not to say anything about markets (120 companies, 2009 to 2022, seed 7; every command is in the chapter, and the figures were re-run in the second round on the more realistic world described below): the planted free-cash-flow-yield effect reads as a mean rank IC of +0.059 (95% interval +0.044 to +0.074, t = 7.8) and is positive in all 14 years; the 80-formula search (standard bars) tested 70 in full and gave six Candidates with a probability of backtest overfitting of 5%; the top-30 long-only book earned 26.3% a year against 15.8% for owning everything equally (alpha 8.6%, beta 0.99, a breakeven cost of 925 bps); and, fed three alphas of which one points the wrong way, weighting by recent IC recovered +0.038 where equal weights gave +0.003 (the best single alpha alone gave +0.059, so no combination beat the best part) and a ridge model did not clearly beat the simple rules.

What holds the grade back: **real data has barely been met.** The OpenFilings adapter was written from the published documentation and tested against stand-in answers of the documented shape; no key was available in this environment. Its first use with a live key (its user's) fetched a company for 11 credits and brought back only a few years of history, and nothing published settles why (a limit on the length of a series, or nothing earlier in the provider's data); the Yahoo symbol mapping and the real filing dates are unknown until three or four more companies have been fetched and the Data quality card read, and no study has been run on real companies. Annual statements only: the provider does not document the fiscal-period values for quarters and a guess costs ten credits, so factors that need quarterly figures cannot be built from real data. The free plan buys about nine new companies a day (about eleven credits each, of 100 a day), so a universe of 500 takes more than five months, and a search over a few dozen companies has little power. Simulated returns are calmer and steadier than real ones (the equal-weight universe has a Sharpe ratio of 1.1, where it was 3.3 before the second round), so only the differences mean anything. The look-ahead audit shows almost no gap on the demo world (+0.059 honest, +0.058 naive) because its filing lags are short; it does flag a world in which net income is known a quarter early, and it has not met real filings. Sectors are as of the day they were fetched, and any database built from today's tickers is survivor-biased. The bars for *Validated* are modest by design (one look at a short locked block cannot support more) and should be raised before any decision about money. And a long job waits behind the app's one worker, though each view of the tab keeps its own job in view.

### The second round: what an A would need, and what was done

The question was what separates this tab from an A, and it was answered the way the first grade was: by using every view in a real browser (a desktop width and a phone's, light and dark, with the real database empty and with the demo), by reading the statistics for what a careful reader would ask of them, and by planting bugs in the research code to see whether the tests notice. The findings, then what was done about each.

**What stood between B and A: using it.** On a first visit to an empty real database there was no order of work (tiles of zeros and no next step), the credits left were invisible until a fetch was refused, and after statements were fetched the way to the prices was a hunt. The Overview went on showing the old counts after companies were added or prices loaded, until the page was reloaded. The headline over a study could say *Some evidence* above a sentence that began *Strong in-sample evidence* (a clear signal with a net Sharpe of 0.43), and a t between 1.65 and 2 was *No clear evidence* above *Some evidence*. A button pressed while its view was still reading was silently refused ("Still working") and looked broken, and the keyboard's place was lost. At a phone's width a wide table could not be reached from the keyboard, a heading skipped a level, and nothing could be taken to a spreadsheet.

**What stood between B and A: the statistics.** A study gave an IC and a Sharpe ratio without saying how sure they were, and never said what it could have seen at all, so *No clear evidence* from thirty companies read as *no effect*. The only guard against luck in a search was the correction for the number of ideas tried; nothing measured whether the search, as built, passes things that cannot be there. There was one set of bars, a lenient one, and the count of ideas tried began again with every run. A rank IC could not tell a factor from size, beta, volatility or momentum under another name. The look-ahead audit asked what a figure would be worth if it were known at its period end and not what it is worth if it is used late. And the simulated world, on which every figure in the chapter was measured, made each month's days a straight line between its month ends: a daily volatility of 4% and an equal-weight Sharpe ratio of 3.3, which flatters anything that trades and hid that one of the new statistics was nearly blind to a skewed signal.

**What was done.**

- *Guidance and state.* A checklist that opens the Overview until the database is ready (key, companies, statements, prices, and enough companies to see a real signal), each step ticked when done and each with its button; meters of the credits left today and this month; prices offered with one click after a fetch; the Overview and the explorer read again after any change of data; the work buttons off while their view works, with the focus handed back; one rule (`evidence_level`) for the headline, the sentence and the terminal; CSV downloads of the scan, the leaderboard, the library and the graveyard with numbers as numbers; a scrollable table reachable from the keyboard at 390 px and no skipped heading. An axe-core audit of 33 states (every view, light and dark, a phone's width) finds nothing.
- *How sure.* A 95% interval on the mean IC and (Mertens) on the Sharpe ratio; what the study could have seen (the minimum detectable effect and the chance of seeing a true IC of 0.01 to 0.08), and the same before a search is run (`preflight`); a Fama-MacBeth premium with controls, judged by the per-date difference and not by which version is significant; a look-ahead audit that also waits 1, 30, 60 and 90 days.
- *Against luck.* Three named sets of bars (exploratory, standard, strict) with standard the default of the page, the routes and the command line; a ledger that counts the ideas of every earlier run on the same question; and `placebo`, which repeats the search on shuffled returns and counts what gets through every screen anyway (with an exact interval), whether the t-statistics have the spread of 1 that a correct one has, and, set beside a real run, what share of its survivors that makes luck. On the demo world, five shuffles of 200 formulas let 0.6 formula per shuffle through every screen under the standard bars (0.1 to 1.8 allowing for chance), 1.2 under the exploratory ones and none under the strict ones, and the t-statistics were a little generous (a spread of 1.17, 95% range 1.00 to 1.35, and 10.4% of shuffled formulas past |t| of 2 where 4.6% is correct; 25 shuffles in five batches gave 1.23, so luck passes the first screen about twice as often as its name says).
- *A world that is harder.* The simulated days now bridge their month ends (exact to 1e-9) and are as volatile as the month says (an equal-weight daily volatility of 14%, a Sharpe ratio of 1.1); every figure in the chapter and the guides was re-run on it. The results changed less than the worry suggested (free-cash-flow yield +0.057 to +0.059, t = 8.0 to 7.8; the long-only book 3.54 to 1.58 in Sharpe because the benchmark's fell from 3.28 to 1.07 with it).
- *The years a company holds.* The first fetch with a live key cost 11 credits and brought back a few years, and the tab could neither say why nor let the rest be asked for. Now the company page says in words what the last request asked for and what came back (the window, how many annual statements, the entries of other kinds that were left out, the window OpenFilings says it ran when that differs from the one asked, and the note it adds to an answer); when the series starts later than the request it says that either nothing is held that early or the length of a series is limited, which the provider's pages do not settle, and that asking for the early years alone settles it for the same price. A calendar shows every fiscal year of a company as held, missing, asked for with nothing sent, due or not yet due. Picking years prices them before anything is spent (*One request for FY2014 to FY2016: 10 credits*): the price is per request, so the years picked become one request, the plan is worked out on the server, and the fetch will not start without the budget the plan showed. It never asks for a year that is held and never writes to one; a year found empty is left out until it is picked again (a newer year found empty is offered again after a month, since a late filing may have appeared); and any other year that comes back inside the window is stored, since it was paid for. Quarterly statements already held are listed beside the calendar and cannot be requested: the provider documents no value for a quarter, and a guess costs ten credits. 47 tests (40 on the rules, the service and the stand-in provider, the rest over HTTP, on the command line and in a real Chromium); axe-core found nothing in 8 states (light and dark, 1,400 and 390 px wide, the real database with three years picked and the demo's read-only view). The module's own bug-planting audit is described below.
- *Test depth.* `experiments/plant_bugs.py` changes one operator, comparison, sign or number at a time and runs the tests. On the research code of this tab (eleven modules) it made 355 changes, drawn at random, and 162 of them made a test fail the first time (46%). The survivors were read one by one. Many are harmless (a bound that no data touches, a number in a message, a hyper-parameter's default, a guard that repeats a check made upstream such as a free-cash-flow fall-back for a figure the database already derives); the rest were places where the tests did not check what the line did: the compound growth rate and second differences, the tax-rate limits and the floor of invested capital behind a return on capital, an average of balances, the sign of an F-score at exactly zero, the lags of the overlap-corrected error and the Sharpe interval of a flat series, the default bars and the weights of the fitness, the edges of the verdict, the weights of a leg, the two decisions of the look-ahead audit, the minimum size of a group and a regime, the assumed filing lags and the age limits of a figure, and the trailing sums over quarters and halves (a missing quarter, the one-tenth rule). Each got an exact-value test, and the lines where a change had slipped through were put back against the new tests, in eight of the modules (analytics, evaluate, expression language, library, metrics, point-in-time tables, research context, transforms) up to four times as further survivors were read. At the last look 28 changes on those lines were still not noticed. Sixteen cannot change any result: a guard that repeats what a calculation already gives (a spread tested for being positive before a division, weights that add to zero giving zeros either way, a ratio guarded by a finite check one line on), a fill value on a mask that never has a hole, the order in which two metrics are computed, a clip at the 0th and 100th percentile, a sort that is redone later, a tie at ten per cent that needs one exact decimal, a time scale applied to both sides of a search, a mask aligned by label. Twelve are choices inside the random formula generator (the odds of each kind of formula, how many tries it makes, which fields count as ratios), whose tests check that what comes out is well typed, repeatable and varied and not how it was chosen, and a seeded test could only restate them. The bridge, the combiner and the discovery loop had their survivors read and the meaningful ones tested but were not put back against the new tests, so how many of their 78 first-time survivors are still unnoticed is not known.

The same audit on the data layer (key pool, credit meter, OpenFilings adapter) made 130 changes and 83 were noticed the first time (64%); the survivors were what a pool may spend and how each refusal is logged, the quota's day and month edges, and the adapter's reading of a search (a ticker of five capitals, a name of eight letters), the country of a company and an account's list of markets. After tests for each, 4 changes are still not noticed, none of which can change a result: guards on a state the pool never reaches (3) and the cap of 32 million bytes read from a response (the change adds one). On the new years module it made 154 changes and 140 were noticed (91%); the survivors included one real flaw, which is fixed with a test: a request made before a year's filing was due counted as having asked about it, for a year older than the latest one held, so the year would not have been offered again. Three changes there are still not noticed, each the comparison of a year with the latest year held, which is never asked about because it is held.

What the audit does not show: it plants one small change at a time at places drawn at random, so it samples each module and does not cover every place; whether a change is *equivalent* is my reading and could be wrong; it is run by hand and not in CI; and it measures whether the tests notice a change, not whether the tests ask the right question.

**What the new checks caught in themselves**, each fixed with a test: the premium regression was nearly blind to a signal with a skewed spread (a yield with a skew of 6.7) until the signal entered as the normal score of its rank, after which a planted premium of 0.68% was recovered (0.72%, t = 7.1); its first reading compared whether each version was significant, which says nothing about whether they differ, and now tests their per-date difference; the calibration gave a verdict on the spread of the t-statistics from 87 formulas, more than that number can support, and now withholds it below 150; its first error for that spread (+-0.06, from 3 shuffles) was about five times too small, because the formulas of a search share the returns that were dealt out and move together (a run of 25 shuffles in five batches gave 1.18, 1.30, 1.25, 1.24 and 1.20), so the error now comes from the scatter between shuffles, is not given for fewer than three, and five shuffles are the default; a per-run warning that a finalist's q-value could not be within the bar was wrong (Benjamini-Hochberg allows a share of runs by design) and is gone; a flat series of information coefficients was given a skewness by a division by its zero spread; and a press during a read was refused, which the continuous-integration browser job found on a slower machine than mine (the test now waits, and the page no longer lets the press happen).

**Why it is B+ and not an A.** An A would need what nothing here can supply, and the table above says so: **the OpenFilings adapter has met a live key only once**, and that one company came back with a few years of history for a reason that is still not known (a few more companies and a read of the Data quality card are the real test of the adapter, the Yahoo symbol mapping and the real filing dates); **annual statements only** (quarterly figures cannot be built from real data, and the provider documents no fiscal-period values for them); **every number is measured on a simulated world** (more realistic now, still without the clustering, regime changes and fat tails of real returns, so the bars, the placebo's reading of the t-statistics and the power table are unvalidated on real data); and a real universe of a few hundred companies takes months to collect on the free plan. What the second round did is remove what could be removed without them: the questions I could think of that a careful reader would put to a study, a search or a page now have an answer in the tab itself. The grade moves up one notch because the evidence behind it is stronger and the tab says what it can and cannot see; it does not move to A because the gap that is left is the one that matters most. A regrade to A should follow a run with a live key, quarterly statements if the provider documents them, and the placebo and the bars re-measured on real companies.
